# W1 作业：命令行文档转 Markdown 工具

## 一、场景与目标

平时工作中，资料分散在飞书云文档、Word、PDF、PPT 和 Excel 等文件中，不便直接作为大模型输入。本作业实现一个命令行工具：输入线上文档地址或本地文件路径，提取正文并通过 LLM API 规范 Markdown 格式，生成可继续用于问答或检索的 `.md` 文件。

本项目只做文档转换，不包含工作管理、数据库、RAG 或复杂 Agent Loop。

## 二、核心功能

1. **交互式输入**：启动后粘贴本地文件路径或飞书新版 `/docx/` 链接，支持连续转换，输入 `exit` 退出。
2. **多格式读取**：本地文件由 MarkItDown 提取；飞书文档通过 Browser MCP 在已登录、已有权限的 Chrome 中读取。
3. **LLM 格式整理**：使用 OpenAI 兼容 API，要求模型保留原文、数字、链接、代码和顺序，规范标题、列表等 Markdown 结构，并在正文末尾追加「文档总结（AI 生成）」章节，以 1–5 条要点概括原文。总结不替代正文；纯本地模式不生成总结。
4. **自动保存**：统一输出到 `output/`；保留 `.raw.md` 便于核对，重名自动追加编号，不覆盖文件。
5. **基本防护**：发送前人工确认；支持 `--local-only`；限制输入长度、请求超时，并拒绝将空回复或截断回复保存为成功结果。

## 三、技术方案

```text
本地文件 → MarkItDown ───────────────────────┐
                                          ├→ 原始 Markdown → LLM API → 最终 Markdown
飞书链接 → Browser MCP → Chrome → 文档块提取 ┘
```

开发语言为 Python 3.12，使用 MarkItDown、OpenAI Python SDK 和 MCP Python SDK。飞书页面提取使用一个小型 JavaScript 脚本处理文档块和滚动。

正式使用的默认模型配置为公司部署的 GLM-5.2：

```dotenv
LLM_BASE_URL=http://221.131.102.69:18088/v1
LLM_MODEL=glm-5.2
LLM_API_KEY=<你的 key>
```

程序显式调用 MCP 工具，模型负责整理文本。本项目没有声称实现模型自主选择工具的多轮 Agent。

## 四、关键设计

- **提取与整理分离**：工具负责取得真实正文，模型不根据链接猜测文档内容。
- **保留原始结果**：模型可能改写或漏字，保留 `.raw.md`，便于人工对照。
- **最小可用范围**：先支持常见文件和飞书新版文档，不引入页面、数据库等无关功能。
- **权限边界**：能访问文档不等于允许向模型发送文档；调用前必须确认数据使用权限。

## 五、验证与当前限制

已完成本地格式提取、自定义输入校验、自动命名、交互流程和模型异常处理的自动测试，共 10 项通过，新增总结缺失或为空的输出校验；格式测试覆盖人工生成的 DOCX、文字 PDF、PPTX、XLSX、HTML、TXT 小样本。飞书独立程序已验证可读取正文。

默认 GLM-5.2 接口的 `/v1/models` 已返回模型列表，但此前生成请求发生超时；正式配置下的端到端成功结果及截图仍需补充验证。自动测试不等于真实模型调用成功。

飞书 DOM 提取不能保证全文完整，复杂表格、图片、附件、折叠和嵌入内容需人工核对；扫描 PDF 暂不支持 OCR。模型单次处理上限为 12000 字符，超过时保留原始结果，不自动分块。
